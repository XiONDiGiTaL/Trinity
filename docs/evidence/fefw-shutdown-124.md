# fefw 0.2.13 `--max-seconds` exit investigation

Date: 2026-11-25
Runtime: `X:\fefw-recomp-0.2.13\fefw.exe` (0.2.13, build `bab923d`, SHA-256
`382645ba09fadc800d459e3fa72b4a7ba87281152e9935d329beb783035cb8b1`)
Host: Windows x64, AMD Radeon RX 7900 XT, headless Vulkan

## Result

There is no 120-second shutdown hang in `fefw.exe`. The process exits about one
second after the deadline is logged. Exit status `124` is generated by fefw
itself, not by the `timeout` wrapper.

Measured wall time around the process, not around a log tail:

| Runtime | `--max-seconds` | Wrapper | Wall time | Status |
| --- | ---: | ---: | ---: | ---: |
| fefw 0.2.13 | 5 | `timeout 40` | 6.130 s | 124 |
| fefw 0.2.13 | 25 | `timeout 45` | 26.136 s | 124 |
| fefw 0.2.13 | 25 | `timeout 120` | 26.052 s | 124 |
| ObeliskChamber 0.3.2 | 5 | `timeout 30` | 6.008 s | 124 |

The 25-second runs logged the deadline at about 25.49 s, and the process was
gone by 26.05 s. `tasklist` showed no remaining `fefw.exe` after each run.

## Why the wrapper report was misleading

GNU `timeout` uses status `124` for its own timeout. It also passes through a
child's status `124`. A wrapper that only checks `$?` therefore cannot tell:

- the child exited deliberately with `124`, or
- the wrapper killed the child after 120 seconds.

The measured wall time resolves the ambiguity. The 120-second run returned in
26.052 s, not 120 s.

The status is intentional. In the `v0.2.13` tag,
`game-build/fefw/src/fefw_main.cpp` logs the deadline and calls:

```cpp
TerminateProcess(GetCurrentProcess(), 124);
```

immediately after the state summary and log flush. The last log line is exactly
the `state at the deadline` line produced just before that call.

## Is this runtime, shader cache or Trinity shutdown?

It is none of those. It is the runtime's documented deadline exit.

- **Runtime:** `--max-seconds` is defined to end the process with code `124`.
  The installed 0.2.13 binary uses the immediate `TerminateProcess` path; its log
  says `ending the process`, matching the `v0.2.13` source.
- **Shader cache:** the deadline path does not call `nxrt::shutdown()` or save
  the shader cache. There is no cache worker to join before the process ends.
- **Trinity:** the deadline path does not unload mods or call a Trinity shutdown
  hook. `TerminateProcess` bypasses DLL detach and `atexit` handlers, so Trinity
  cannot hold this exit open.

The working tree also contains a newer, unbuilt fefw source path that runs
`nxrt::shutdown()` on a separate teardown thread and waits at most 15 seconds
before calling `TerminateProcess(..., 124)`. Even that newer path cannot produce
a 120-second wait. The installed 0.2.13 binary does not emit its `ending the run
through the end-of-run teardown` message, so it is not running that code.

## Reproduction

The runtime was started with the supplied 1.1.1 dump and the same three mods,
headless, using a test INI derived from `fefw.ini`:

```text
timeout 120 ./fefw.exe --headless --max-seconds 25 \
  --ini X:/fefw-recomp-0.2.13/fefw-shutdown-test120.ini
```

The wrapper returned at 26.052 s with status `124`. The effective log was
`fefw-shutdown-test120.log`, selected by the test INI's `[log] path`.

The shorter runs used the same executable and configuration with
`--max-seconds 5` and `--max-seconds 25`, and wrapper limits of 30 s, 40 s and
45 s. All exited normally at deadline plus startup time.

## Recommendation for test harnesses

Treat `124` as the expected fefw deadline status when `--max-seconds` is set.
Do not infer a timeout from `$?` alone; record the elapsed wall time and the
child PID, or map the expected `124` after the configured deadline. A wrapper
around a launcher or another parent process must track the actual `fefw.exe`
child, not just the launcher process.

`tools/check_fefw_deadline.py` implements this: it starts fefw itself, waits
until `--max-seconds` plus a grace window, passes on the runtime's `124` and
reports an overrun only when the process has to be killed at that limit.

## Limits

- These are headless runs on one Windows host.
- No windowed run, gameplay, save, turn or panel interaction was exercised.
- The test covers `fefw.exe`; a separate wrapper may have its own reason to
  wait if it supervises a different process.
